# Changelog

All notable changes to **Universal Hardware Description (UHD)** will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Library protocol draft 3: definition source (`docs/library-protocol.md` § 4.6). A revision's `source` record may carry the TypeScript its definition is written in, like an npm package's code: `files` (the source closure, blobs by SHA-256), `entry`, `export`, and `requires` (`uhd`, a peerDependency-style version range that must admit `uhdSchema`, and `typescript`). It is outside the envelope digest and checked by evaluation instead: the source evaluates to the definition digest when its entry's export, as JSON, has the definition file form whose SHA-256 is `definitionDigest`. Library source is limited to declarative definition code: static imports of `@deltarobotics/uhd` and its own closure only, no host globals (`process`, `fetch`, `eval`, `Function`, timers, …), no dynamic import or `import.meta`, every file reached from the entry. New capability `source`. `@deltarobotics/uhd/library` adds `lintSource`, `sourceImports`, `resolveSourceImport`, `tokenizeSource`, `sourceProblems` (also run by `envelopeProblems`), `evaluatedDefinition`, `evaluatedDefinitionDigest`, `verifySourceFiles`, `satisfiesRange`, `isVersionRange`, `minVersion`, and the types `SourceFile` and `SourceRequirements`; the JSON Schema gains `#/$defs/sourceFile` and `#/$defs/sourceRequirements`; the conformance kit adds the check `revision.source` (files, lint, and with `evaluateSource` the digest).
- Definition source is evaluated confined (§ 4.6.3): a consumer never imports source it did not write into its own process. `@deltarobotics/uhd/library/confined` adds `evaluateSourceConfined`, which evaluates each closure in a child Node.js process of its own under the permission model (reads only the closure and UHD's `package.json` and `dist`, no writes, processes, workers or addons), with code generation from strings disabled, an empty environment, and a time, heap and output limit (`timeoutMs`, `maxHeapMb`, `maxOutputBytes`; a child that writes more than the limit is stopped and none of it is kept). Closures share no process, so one cannot alter another's result or write a result in its name, and one that hangs or exits fails alone; `concurrency` sets how many run at a time. The lint (§ 4.6.2) also refuses `Reflect`, `Proxy`, `this` outside a class, the properties `prototype`, `getPrototypeOf`, `setPrototypeOf`, `getOwnPropertyDescriptor(s)`, `defineProperty`/`defineProperties`, and any string or template text whose value (escapes decoded) is one of the forbidden property names, such as `f["constructor"]`.
- Conformance kit, `revision.source`: when the examined revision ships no source, the kit looks through the other parts search found until one does (at most `maxSourceParts`, default 25), instead of stopping after the first.
- Mechanical drive-train and fastening vocabulary, and serial, IR, mains and coil links (`docs/mechanical-interfaces.md`, `docs/links-and-buses.md`). `BoltPattern` shapes `grid` (rectangular or triangular lattice, `pitchMm`/`pitchYmm`, rows × columns or a disc `withinDiameterMm`/`minDiameterMm`; derived `hole_count`, new parameter `hole_pitch_y`) and `arc` (a partial bolt circle: `holeCount`, `angularPitchDeg`, `startAngleDeg`; new parameter `angular_pitch`), with `latticeHoles`, `arcHoles`, `patternHoles`, `holesFitOn` and the pair check `bolt_pattern_holes` (the pattern with fewer holes must land on the other's under a rotation, shift or mirror; a grid fits a slot). `Shaft({ clampsOn })` for a round bore that goes over another profile and clamps on it (a collar's Ø6 bore on a 5 mm hex), checked by `shaft_fit`. New builders: `Gear` (`gear_mesh: mesh`; module or diametral pitch, pressure angle, teeth, face width; spur, helical, internal, rack, bevel, worm, worm wheel), `Bearing` and `BearingSeat` (`bearing_fit: bearing/seat`, plus the bearing's `Shaft` bore; ball, roller, needle, tapered roller, thrust and plain bearings), `Thread` (`thread: external/internal`; designation, diameter, pitch or TPI, length, hand, lock), `TSlot` (`t_slot: track/insert`; opening, channel, neck and head), `AxialFace` (`axial_stop: face`; spacer, collar and hub faces), `Wheel` and `RollingSurface` (`rolling_contact: wheel/surface`), `RS485` (`rs485: node`, half or full duplex), `RS232` (`rs232: dte/dce`, straight or null modem by sub-role), `SWD` (`swd: target/probe`), `PPM` (`ppm: output/input`), `InfraredRemote` (`ir_remote: transmitter/receiver`, network domain), `AcPower` (`ac_power: input/output`, V RMS and line frequency, plug and earth), `InductiveLoad` and `InductiveDrive` (`inductive_load: load/driver`, coil current, suppression, switching). New parameters `gear_module`, `pressure_angle`, `tooth_count`, `face_width`, `bearing_od`, `bearing_bore`, `bearing_width`, `seat_depth`, `thread_length`, `slot_opening`, `channel_width`, `channel_depth`, `neck_width`, `head_width`, `head_height`, `face_od`, `face_id`, `axial_length`, `wheel_diameter`, `tread_width`, `load_rating`, `line_frequency`, `ir_carrier`, `coil_current`, `coil_resistance`. New pair checks `checkPairDrive` (`gear_mesh`, `bearing_fit`, `thread_fit`, `t_slot_fit`, `axial_face`, `rolling_contact`) and `checkPairSignals` (`rs485_duplex`, `rs232_null_modem`, `ppm_channels`, `ppm_polarity`, `ir_link`, `ac_power`, `inductive_load`), run by `validatePair`; the overlap check skips what they compare (`driveCheckedParams`, `signalCheckedParams`). Role tables for each, with no generic fallback except `swd`.
- Board rules for a part's own pins (`partWiringRule`, rule `net`, `docs/boards-and-nets.md`): a passive with every terminal on one net is shorted (`net:<net>:shorted:<part>`); a part's power output on one net with a power input of the same part that feeds it, by its `bridgesTo` or, for a part that states none, any input, is an output tied to its input (`net:<net>:feedback:<part>`); a leaf with the new `strap` trait (`StrapTrait`: `function`, `when`, `levels`, `source`), while its part runs an interface in `when`, on a net with another pin's logic signal and no supply or ground pin, follows that signal (`net:<net>:strap:<pin>`).
- Intentionally unconnected interfaces: `ChildModuleRef.unconnected` lists interfaces an instance leaves open on purpose, each with a reason (`UnconnectedInterface`), like a no-connect flag on a schematic: a DC jack unused because the product runs from USB, a motor supply terminal waiting for a battery. The `unpowered` rule reports a marked power input as info with its reason instead of a warning; the new system rule `unconnected` warns when a link connects a marked interface or a mark names an interface the child does not have. `unconnectedOf(ref)` reads the marks.
- Connectors that ship loose: `ConnectorDetail.supplied` (`"fitted"`, the default, or `"loose"`) says a connector comes in the bag and is fitted during assembly, such as a shield's header strips that the builder solders; `Connector()` and `connectorTrait()` record it, and `looseConnectors(def)` lists them so an assembly plan can add the soldering step.
- I2C addresses other than the device's own: `I2C({ otherAddresses: { all_call: 0x70 } })` writes `i2c_address_<name>` parameters for addresses a device also answers at by default (a PCA9685's all-call address, enabled sub-addresses); `i2cAddresses(iface)` lists them after `i2c_address`. The `bus_address` rule counts them: two devices may share an all-call address, but a device whose own address is another's all-call or sub-address is an error.
- Link, bus and radio vocabulary (`docs/links-and-buses.md`). Builders: `PCIe` (protocol `pcie`, root ↔ endpoint; `lane_count` [1, lanes] and `pcie_generation` [1, highest]; optional lane pairs named from the port's side, REFCLK, PERST#, CLKREQ#, WAKE#); `M2` (socket ↔ card; `m2` trait with key, sizes, carried interfaces, socket number); `CSI2` and `DSI` (transmitter ↔ receiver; `lane_count` from lane modes, `lane_rate`, D-PHY clock and data pairs); `Ethernet` (port ↔ port; copper MDI pairs a–d or fibre with mode and wavelengths; `link_speed`; PoE PSE or PD with standard, class, `poe_power`) and `SFP` (cage ↔ module, form); `I2S` and `PCM` (clock controller ↔ target, older master ↔ slave; data direction; frame formats; `sample_rate`, `bit_depth`, `channel_count`); `DVP` (camera ↔ host, data MSB first so a wider camera lands its upper bits); `SDCard` (host ↔ card; form, bus modes, capacity classes); `USB` (host ↔ device, dual_role, older bidirectional; speeds; D±, SuperSpeed pairs, CC); `WiFi`, `Bluetooth` and `IEEE802154` (network domain, `wireless` trait with bands and stacks; 802.15.4 for Zigbee, Thread and Matter); `Led` and `LedDrive` (LED terminals as passive leaves with `led_drive` anode/cathode composites; driver channels sink ↔ cathode, source ↔ anode; `led_current`); `RelayCoil` and `RelayContacts`. Traits `LedTrait` (`ledTrait`), `RelayTrait` (`relayTrait`, poles and throws from the contact form) and `StorageTrait` (`storageTrait`, capacity in bytes, volatility from the medium). Shared plumbing `linkSlots`, `diffSignals`, `DiffPair`. Role tables for each protocol with per-conductor sub-roles and no generic fallback. New parameters `lane_count`, `pcie_generation`, `lane_rate`, `link_speed`, `poe_power`, `sample_rate`, `bit_depth`, `channel_count`, `bus_width`, `rf_band`, `wavelength`, `led_current`, `forward_voltage`. New pair checks (`checkPairLinks`, run by `validatePair`): `link_width`, `lane_rate`, `m2_key`, `m2_size`, `m2_interface`, `ethernet_speed`, `ethernet_medium`, `fiber_mismatch`, `poe_power`, `sfp_form`, `audio_format`, `audio_direction`, `dvp_width`, `sd_form`, `sd_mode`, `sd_capacity`, `usb_speed`, `led_drive_current`, `wireless_band`, `wireless_stack`, `zigbee_roles`; the overlap check skips the parameters they compare (`LINK_CHECKED_PARAMS`, `linkCheckedParams`).
- Taxonomy 1.2.0: 10 nodes added after the source's own children: `component.storage` with `.memory`, `.memory_card` and `.ssd`; `connectivity.wired.ethernet`; `connectivity.wireless.ieee802154`; `expansion.pcie`; `mechanical.fastener.standoff`; `component.ic.analog_switch`; `component.ic.led_driver`. The 77 ProtoPart nodes are unchanged.
- A nut on a threaded shaft: when a fastener harness's structure-side interface is a shaft whose `shaft` trait states a `thread` (a motor's M5 prop shaft), `assemble` takes the shaft as the screw of any nut in the stack, from the shaft's frame outward (to its `length` parameter when stated), so a prop nut is placed and checked on thread like any other nut. A shaft that states no thread is still no screw.
- Mechanical and current-rating vocabulary for structural kits, motors and linear actuators (`docs/mechanical-interfaces.md`). `BoltPattern` shapes `row` (`pitchMm`, `holeCount`; new parameter `hole_pitch`, `hole_spacing` is the span) and `slot` (`slotLengthMm`, `slotKind` `t_slot` or `through`; new parameter `slot_length`), with the pair check `bolt_pattern_line`: a row mates a row whose holes land on its own (same pitch or a whole multiple, no longer) and a slot at least as long; two T-slots do not mate; a row or slot never mates a square, circle, cross or two-dimensional rectangle. A rectangle with `spacingYmm` 0, the older encoding, reads as a two-hole row, or as a slot when its spacing is a range from 0. `boltPatternHoles` places a row's holes and returns none for a slot. `Shaft` gains `gender` (`shaft` or `bore`), `profile` (`round`, `hex`, `rounded_hex`, `d_cut`, `double_d`, `keyed`, `spline`, `square`), `keyWidthMm` (parameter `key_width`), `spline`, and the role `bidirectional` for shafts, spacers and couplers that carry torque from a driver to a load; the pair check `shaft_fit` refuses two shafts, two bores and profiles that do not fit (a hex shaft in a round bore, different splines) and warns when a key goes unused. `LinearMotion` (protocol `linear_motion`, output/input) with parameters `stroke`, `lead`, `thread_pitch`, `force`, `linear_speed` and a `linear_motion` trait (mechanism, starts, backdrivable); the pair check `linear_motion_capacity` requires the output's stroke and force to cover what the load states. `minSupplyCurrentA` on `PowerIn` and on the `input` side of `BrushedMotorTerminals` and `BrushlessPhases` (parameter `min_supply_current`, refused on outputs), with the pair check `supply_current_rating` against the source's `max_current`. `pairCheckedParams` names the parameters the joint checks compare themselves, which the overlap check skips. New parameter builders `minSupplyCurrentA`, `holePitchMm`, `slotLengthMm`, `keyWidthMm`, `strokeMm`, `leadMm`, `threadPitchMm`, `forceN`, `linearSpeedMmS`.
- Motion, bus, connector and fluid vocabulary: `StepperPhases` (bipolar and unipolar windings, `bipolarCapable` six-wire motors) and `StepDir` (STEP, DIR, ENABLE with optional opto returns, step rate and timing); `BrushedMotorTerminals`; `QuadratureEncoder` (A, B, index, absolute PWM, supply); `ServoPort` (signal, V+, ground, pulse width and frame rate); `CAN` (bus side, bit rate, FD, termination) and `CANLogic` (controller TX/RX to transceiver TXD/RXD); `ShieldHeader` with the Arduino UNO R3, Arduino ICSP and Raspberry Pi 40-pin layouts as connector composites; the `cross` bolt pattern shape (two diagonals) with its hole geometry; and `FluidPort` for pneumatic and hydraulic ports (`docs/fluid-ports.md`, with general guidance for mapping other libraries' fluid ports). Role families in `matching/roles.ts` for steppers (output/input and the older driver/motor), CAN (node, transceiver and peer as one bus family; controller ↔ transceiver on the logic side) and fluid flow (source, sink, bidirectional, sensing); these protocols can opt out of the generic role pairs. New parameters `pulse_width`, `frame_rate`, `counts_per_rev`, `bit_rate`, `pressure`, `tube_od`, `tube_id`. New pair checks (`checkPairJoints`): `fluid_joint_mismatch` and `bolt_pattern_shape`. A BSPP or BSPT thread size matches with or without its "G" or "R" prefix. A cross with equal diagonals mates a 4-hole circle of the same diameter and a square of side diagonal/√2, which have the same holes (`boltPatternsShareHoles`); the pair check compares the diagonal instead of `hole_spacing` for those pairs.
- Taxonomy 1.1.0: the 77 ProtoPart 2.1.0 nodes now match the source byte for byte (id, order, name, description, docs_url, links, agent notes), checked against a vendored copy of the ProtoPart taxonomy JSON (`test/fixtures/protopart/`). The 26 UHD additions are reworded in the source's style. The file publishes `aliases` for the nine paths ProtoPart parts used outside its taxonomy; `validateCategories` suggests their targets (`alias: true`), and `resolveCategoryAlias` and `migrateCategories` apply them. `validateTaxonomyDocument` checks that an alias is not a node and that its targets are. The kit's `controller_part_id` and `manifest` stay out, as the provenance records.
- Library protocol draft 2: file terms (`docs/library-protocol.md` § 4.5). Every file of a revision envelope (an `artifacts` entry or a carried `evidence` file) may carry `terms`: a distribution class (`redistributable`, `internal`, `unknown`), licence (SPDX id or name), licence URL, licence file, attribution, summary, source URL, source SHA-256 and retrieval date. A revision is redistributable when every file backing a definition artifact is; a library may decline other files with `403 NOT_DISTRIBUTABLE`. `FileTerms`, `DISTRIBUTION_CLASSES`, `isRedistributable` and `revisionDistribution` in `@deltarobotics/uhd/library`; the JSON Schema gains `#/$defs/fileTerms`; the conformance kit accepts a refused file whose terms are not redistributable.
- Net rule `net`, drive levels: a digital output that is only an output (not open drain, not an input) on a part with one supply net drives its net up to that supply's voltage; a logic or analog pin on the same net rated below it is an error (`net:<net>:drive:<pin>`, details `driver`, `supply`, `level`, `pin`). It catches an MCP73831's tri-state STAT (high at its VDD, VBUS) wired straight to a 3 V GPIO. Parts with several supplies, and open-drain outputs, are left alone.
- Category taxonomy (`docs/taxonomy.md`): a versioned tree of hardware categories, `src/taxonomy/uhd-taxonomy.json` (version 1.0.0, 103 nodes under 11 roots) with its JSON schema, derived from the ProtoPart category taxonomy 2.1.0 (every 2.1.0 path kept; names and descriptions reviewed for hardware in general; 26 nodes added; provenance recorded in the file). `ModuleDef.categories` holds taxonomy paths at any depth; `tags` stay free-form. Helpers: `UHD_TAXONOMY`, `buildTaxonomy` (node by path, children, breadcrumbs, every node), `categoryAncestors` (for subtree filtering), `categoryMatches`, `countCategories`, `categoryParent`, `isCategoryPath`, `validateCategories` (unknown and malformed paths, with suggestions), `taxonomyTree` (JSON with counts), `validateTaxonomyDocument`, `compareTaxonomyVersions`. Also exported as `@deltarobotics/uhd/taxonomy`, with the JSON files as package exports. The code loads a generated copy of the JSON (`uhd-taxonomy.data.ts`, `npm run build:taxonomy`), so no consumer needs JSON-module support; the tests check the two agree.
- Library taxonomy declarations (`taxonomy-extension.schema.json`, `TaxonomyExtension`, `validateTaxonomyExtension`): a library names the taxonomy version its parts use and may add nodes under its own root `x-<library>`; `buildTaxonomy(doc, extensions)` merges them and refuses another major version, nodes outside the namespace and duplicate libraries.
- System rule `unknown_category`: a warning for each category path of the root or a child definition that the taxonomy does not have, naming the instances (`unknownCategoryRule`; `checkSystem(def, lookup, { taxonomy })` checks against a taxonomy with library extensions).
- Library protocol `uhd-library/v1` (`docs/library-protocol.md`): how any host serves parts and any tool reads them, by URL. Discovery (`/.well-known/uhd-library` or `/v1`: name, version, envelope schemas, UHD range, taxonomy version, capabilities, auth hint, page limits); search with `q`, taxonomy path, domain, protocol and tag filters, cursor pagination and facet counts (taxonomy counts per path and ancestor); part detail and revision lists; the exact revision envelope `uhd.part-revision/v1` as the data contract (canonical JSON, definition and envelope digests, dependencies, files, evidence, lineage); dependency closures; content-addressed files; error codes; caching and immutability; optional bearer auth. Publishing is out of scope. `@deltarobotics/uhd/library` exports the types, the JSON Schema (`schemas/uhd-library-v1.schema.json`, written by `npm run build:schemas`), a dependency-free schema checker, envelope and closure checks (`envelopeProblems`, `closureProblems`, `sealEnvelope`) and the conformance kit `runConformance(url, { fetch?, token? })`, tested against an in-process library with one fault at a time. Taxonomy paths are opaque dotted strings here; the taxonomy is its own document.
- Boards and nets (`docs/boards-and-nets.md`): a custom PCB is a module whose children are its components, whose nets are `Net` interfaces on the board (protocol `net`, not exposed, optional design `voltage`), and whose edge is its exports. `netLinks` writes one membership link per pin (`<net>.<child>.<interface>`); `validateLink` checks them (`net_to_net`, `net_member_composite`, `net_not_own`). `deriveLinks` walks nets like harness conductors and keeps only pad pairs whose lifted interfaces pair by protocol; over a rail (a net with a supply or ground pin, or a design voltage) only power pins pair, so a logic pin tied to a rail is a strap, and ground pins share their net without a link per pair. Supply budgets, bus addresses, interface reuse and unpowered inputs work over boards. `LinkResult.derived` gains `nets`. New system rules `net` (fewer than two pins, a pin on two nets, several supplies on one net, ground joined to a supply, a supply pin outside the net's design voltage, a logic pin rated below it), `bus_pullup` (I2C over nets with no pull-up to a supply) and `design_envelope`.
- Package facts: `PackageSpec` on the mechanical domain (`package`: manufacturer name and code, pin count, pitch, exposed pad and its designator); `partPackage` reads it with the overall size. `pinTable` declares a chip's pin table (every pin with its designator and a cited `pin_functions` trait); `pinDesignatorIssues` reports missing, repeated and uncovered designators (part verification tools report it as `[pins]` warnings). Nothing tool-specific (footprints, land patterns, symbols) is part of UHD.
- `Passive()` (two `passive` terminals and a `passive` trait), `PassiveTrait`, and `DesignEnvelopeTrait` (largest outline and keep-outs a custom module must meet).
- Series passives with the value per placement (`docs/boards-and-nets.md`, "Series passives"): `PassiveTrait` declares the series fields (`series`, `parameters`, `choices`, `overridable`, `tolerances`, `values`, `part_number` with `PassivePartNumberRule`, `PassiveToleranceGrade`, `PassiveValueRow`, `PassiveChoice`). `passiveInstance(def, overrides)` resolves one placement (`ChildModuleRef.overrides`) against the part's own rules: value, tolerance, MPN, parameters and problems; `passiveOf(def, overrides)` gives the trait as placed; `overridableKeys`, `PASSIVE_VALUE_PARAMETER`, `rkmCode`, `rkmValue`, `eia3Code`. New system rule `passive_override` (error): overrides a part does not allow or that disagree with its series, at any depth.
- Example board fixture (`test/fixtures/imu-board.ts`: a microcontroller, an IMU and a buck-boost regulator, all synthetic parts in `test/fixtures/parts/`) with seeded faults.
- Routed harness geometry (`docs/connectors-and-harnesses.md`, "Routed harness geometry"): harness end interfaces may carry frames in the harness's own coordinates; `assemble` places such a harness from the part its first end lands on (`Assembly.harnesses`, `HarnessPlacement`) and checks every other end against its counterpart (stale route → warning). `linkEndFrames` (world frames of a link end, per composed position) and `combineFrames` are exported.
- Connectors and physical harnesses (`docs/connectors-and-harnesses.md`): `Connector()` connector composites (protocol `connector`, positions `p1…pN` bound to pads); link-scoped composition on a link end (`compose`) for pads with no grouping interface; harness conductors as internal `self` links; `deriveLinks`/`systemLinks` trace conductors to functional links, and `checkSystem` runs on stored + derived links. New link diagnostics `connector_mismatch`, `connector_gender`, `connector_positions`, `compose_unknown_slot`, `harness_wiring`, and `bus_incomplete` (a composite lifted over conductors whose required pairing has no conductor inside it, such as SDA landed on an interrupt pin). `ResolvedEndpoint` gains `ownerPath` and `composed`; `LinkResult` gains `derived`; `resolveBelow`, `validateResolved` are exported.
- Drone protocol vocabulary: `BrushlessPhases`, `EscSignal`, `FcEscPort`, `CRSF`, `SBUS`, `BoltPattern`, `Shaft`, `connectorTrait`, and parameters for cell count, capacity, hole spacing, fastener and shaft diameter, burst current, and ESC signal rate.
- Module kinds (`module`, `group`, `harness`), `exports` (child interfaces on a parent boundary; groups export implicitly), stored `links` (`InterfaceLink` with explicit `EndpointTarget`s and optional stored `childLinks`), and `display` hints on `ModuleDef`. Harness endpoints gain topology roles; harnesses gain parameters, artifacts, and traits.
- `src/system`: canonical paths, `primaryInterfaces`, `resolveExports`, `boundaryInterfaces`, `resolveEndpoint`, and `validateLink`/`validateLinks` (per-link DRC on sliced modules, with stored child links overriding derived ones).
- `skills/uhd-authoring`: a reference skill for writing UHD definitions (interfaces, pin tables, buses, connectors, parameters, traits, package facts, geometry frames and refs), with the vocabulary and the evidence-to-UHD mapping rules. It runs no tool. The package ships `skills/`.

### Fixed

- Leads soldered the wrong way round through a harness are incompatible again. When no pair of lifted interfaces pairs by protocol, `deriveLinks` links the largest candidates of one kind (two composites, else the two pads the conductor joins); it used to validate one side's composite against the other's lone pad, which finds the composite's own matching pad and passed the wrong wire (a cell's + lead on a board's BAT- pad). Exposed by merging two sets of board rules (d63a5ed), whose lower-altitude rule made that composite-to-pad pairing unambiguous.

### Changed

- `validatePair`: mechanical interfaces that are interchangeable twins (identical but for id and name: an extrusion's four slots, a bracket's two legs, a plate's bearing seats) are one choice, so one connection is made per pair of twin classes and the other placements stay potentials, and a twin whose clean pairings a twin connection holds does not fall back to one with errors; two shafts or two bores are never auto-connected (potentials only), while an explicit link (`explicit: true`, used by `validateLink`) still reports `shaft_fit`. `Thread` pitch and `AcPower` line frequency may be left out when the source states none; `InductiveLoad` takes leads with no designator; `thread_fit` does not compare a fastener's `length`.
- Board rules as a real board needs them (found on a wearable's main board):
  - `passive` terminals pair with each other (a lead soldered to a pad), but still pair with nothing over a board net.
  - A supply input's stated range must contain the whole rail, not just overlap it. A 3.0-4.2 V cell rail on a 1.7-3.6 V input is an error, reported as "outside its rating at one end".
  - "Driven by N supplies" skips connector pads (a land carries power, it does not make it) and terminals that are both power input and output (a cell's +).
  - `bus_pullup` also reports a net that carries an I2C target's line with no pull-up when no I2C link is derived (a controller whose bus pins are chosen in firmware).
  - Lifting over nets does not pair passive terminals. A composite is lifted only when a non-ground conductor joins its pads, and wired slots that pair with nothing are configured.
  - `unpowered`: a sub-module's export counts as linked when the interface it exports is linked.
  - Pair DRC no longer sees an endpoint's own pins as rivals of the port they belong to.
- `BoltPatternConfig.spacingMm` and `holeCount` are optional in the type (a row derives its span, a slot has neither); the builder still requires them for the square, rectangle, circle and cross shapes. `min_supply_current`, `stroke`, `force` and `linear_speed` are capacity parameters (no pairwise range overlap).
- `Passive()` sets `categories` to the taxonomy path `component.passive.<kind>` (was `passive.<kind>`). The test fixtures use taxonomy paths.
- Derived links: a pad pair lifts to the largest pair of interfaces that pair by protocol, composite with composite or pad with pad; with no such pair a cable still links the largest candidates as before.
- `supply_budget` totals the pins of one power-output port together (a regulator's doubled VOUT pins), counts each load once, groups supplies by instance path rather than definition id (two identical regulators no longer share a budget), and uses a board net's design voltage when the net states one.
- `unpowered` counts the pads a link to a composite carries as supplied (a flight controller's battery input fed through its ESC socket is no longer reported), and does not report inputs supplied through the checked module's edge (an exported input, or any pin on a net with one).
- `defineModule` rejects an export whose id repeats an interface id or another export (it would be shadowed).
- Part-authoring rule: every multi-position connector is a connector composite (`docs/connectors-and-harnesses.md`); `FcEscPort` no longer carries a pinout. `harness_connector` also finds connector composites that bind a link end's pads.
- DRC treats `burst_current` and `drive_current` as capacity parameters (no pairwise range overlap).

### Deprecated

- `ChildModuleRef.exposedInterfaces` (never read); use `ModuleDef.exports`.

### Removed

- The part library. `library/` (parts, their evidence and CAD, the CAD scripts for parts, vendor files and the example quadcopter system), `scripts/build-library.ts` and `scripts/bom.ts` are gone, and the package no longer ships `library/`. Parts come from libraries served over the open library protocol (`docs/library-protocol.md`), which any tool can read; `npm run build:library` now only says so. UHD keeps the schema, pure helpers and the test fixtures its own tests use: an invented quadcopter (`test/fixtures/drone.ts`) for the system, geometry, mass, torque, tool and spin tests, and three synthetic chips (`test/fixtures/parts/`: a microcontroller, an IMU and a buck-boost regulator, invented pinouts and ratings) for the board fixture. Tests that checked library content rather than UHD went with the library, and so did the library's planning document (`docs/showcase-plan.md`).
- `cadArtifacts` and `CadOptions` (`src/authoring/cad.ts`): which files a CAD generator writes is the generator's knowledge, so the helper lives with the generators. `feature`, `own`, `procedural` and `withGeometry` stay. ## [0.1.0] — 2026-05-02

### Added

- Initial public release of UHD as an open-source project under Apache License 2.0.
- Three-primitive data model: **Module**, **Interface**, **Harness**.
- Protocol matching engine with role compatibility (input/output, master/slave, etc.).
- Slot composition: build complex interfaces from leaf interfaces (e.g. I2C from GPIO + pull-ups).
- Capability-based intra-module slot binding.
- Typed parameters with units, ranges, and tolerances.
- Trait system for composable behaviors.
- ASCII and HTML visualizers for module / harness topology.
- Design Rule Check (DRC) specification (see [docs/drc-spec.md](docs/drc-spec.md)).
- Domain examples under `test/fixtures/`: Arduino Nano, L298N motor driver, VL53L0X sensor, DC motor, robot car.
- Architecture documentation: [docs/architecture.md](docs/architecture.md).
